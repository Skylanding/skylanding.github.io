# 2026 年 5 月之后的 Search Agent：记忆、过早承诺，以及它们到底有没有在搜

这个夏天我看 search agent 论文的方式，有点像刷社交媒体：碎片、夹在 rebuttal 中间。ACL 开完、自己也把 Deep Research 类产品用了一阵之后，有几件事不再像实现细节了。

旧图景是 ReAct 加一个搜索 API。新图景更像控制回路：问什么、留什么、何时分叉、以及如何停止把参数记忆当成证据。过去四个月的社区论文，加上几篇工业界笔记，争论的基本就是这四件事。

## 一直反复出现的三条线

**1. Search 是策略，不是一次 retriever 调用。**

MemSearcher（ACL 2026 Findings）把训练侧的问题说得很干净。把整条轨迹拼进上下文，长度会无界增长；改成紧凑 memory，每一轮又变成不同的优化上下文。他们的做法是 multi-context GRPO：把轨迹级 advantage 回灌到每一轮，让写 memory 的策略和搜索策略一起训。这和我在多轮 agent 里反复碰到的 credit assignment 几乎是同一件事。如果奖励只打在最终答案上，模型根本分不清中途那次搜索是有用，还是只是贵。

ITER（2026.8）以及稍早的 LRAT 在 retriever 一侧给出对偶命题：人类点击日志是错误的监督。Agent 在第 *t* 步发出的 query，条件于原问题和此前的子查询。用这条轨迹去训 dense retriever，并把「曾经有用的文档」当成后续步的 redundancy negative，InfoSeek-Eval 和 BrowseComp-Plus 上能抬 7–13%，而且换好几家 agent backbone 都成立。我以前觉得 retrieval 的故事是「换个更强的 embedding」。不是。故事是 *谁在 query*。

训练免费的一侧，HypoSearch（2026.9）是我最近最常推荐的一篇。单轨迹 agent 会过早承诺：看见分叉、选一条、后面每次 tool call 都在给这条路加戏。HypoSearch 先写一组轻量 hypothesis，在有界的独立分支里探索，再比较证据后才提交。Qwen3.5-122B 在 BC-small 上从 46.7 到 60.0，tool call 还少于五条独立 rollout。这和多轮策略里的 tree grafting 几乎是同一直觉：不要让第一条像样的路径独占上下文。

IGPO（EMNLP 2026 Industry，5 月起线上）是不浪漫的那一支。商品目录一直在变，搜索策略不能冻进权重。他们把 *policy guideline* 和 *inventory fact* 拆开，14 天 A/B 报了 3.17% 的 CTR。实验室论文很少谈这个。很多 search agent 默认静态 Wikipedia dump。线上搜索不是这样。

**2. Memory 正在结构化，因为原始轨迹在撒谎。**

ReTree（2026.8）把搜索建成一棵证据树：每个节点存有界摘要、带出处的证据、以及修订历史。新证据打脸旧 claim 时，它走回引入该 claim 的节点，改写，再剪掉被污染的枝。Full-trajectory ReAct 的逐步推理上下文是它的 1.27–1.51 倍，准确率最多低 25.6 个点。有意思的不是压缩本身，而是：没有 provenance 的压缩修不好下游推理，它只会忘。

SearchAtlas（2026.9）是同一想法的诊断版。它把轨迹解析成 evidential query graph，抓到的过程失败和答错的相关性，比拿原始 log 去问 LLM judge 更强：证据碎片化、问题约束根本没传到答案、未经验证的参数知识混进来。如果只打最终字符串的分，你会把 agent 训成流畅的核对器。

Anthropic 那篇 dynamic filtering 笔记（配 Sonnet / Opus 4.6）是工业界的押韵。搜索结果进上下文之前先跑代码过滤：BrowseComp 和 DeepsearchQA 平均 +11%，输入 token −24%。同一论点。瓶颈不是「再多逛几页」，是你允许模型看见什么。

**3. 很多「搜索」只是模型在核对它已经知道的事。**

LiveBrowseComp（2026.5）是让我对 BrowseComp 数字开始不信任的一篇。他们把现象叫做 Intrinsic Knowledge Dependence。Agent 在不用工具的情况下就能答对最多 44.5% 的 BrowseComp；一半以上的 query 来自内部假设而不是检索线索；把支撑证据拿掉之后，它们甚至不如 closed-book 基线。换成 335 道依赖过去 90 天事实的题，closed-book 掉到 2% 以下，带搜索的分数掉 25–40 个点。排名会翻。

这是方法论结果，不是榜单结果。如果训练集和评测共享同一块参数覆盖，你奖励的是 verification。我不会再只用 BrowseComp 去训搜索策略。

## 我会真的去用的 benchmark

评测我会拆成四件事，而不是一个数字。

| 任务 | Benchmark | 为什么 |
|---|---|---|
| 线上困难多跳 | BrowseComp / BrowseComp-ZH | 仍是默认压力测试，但被参数知识污染 |
| retriever 和 reasoner 拆开比 | [BrowseComp-Plus](https://texttron.github.io/BrowseComp-Plus/)（ACL 2026） | 固定约 10 万文档。BM25 + Search-R1 是 3.86%；GPT-5 是 55.9%；GPT-5 + Qwen3-Embedding-8B 是 70.1% |
| 「它真的在搜吗」 | [LiveBrowseComp](https://huggingface.co/datasets/Forival/LiveBrowseComp) | 90 天事实，335 题。把记忆捷径掐掉 |
| 像人的深度调研 | DeepResearch Bench、DR-Arena、LMSYS Search Arena | 长报告和成对偏好。DR-Arena 用实时信息树，和 Search Arena 的 Spearman 到 0.94 |

GAIA、WebWalkerQA、HLE、xbench-DeepSearch、InfoSeek-Eval 仍适合当便宜的回归集。我不会只用其中任何一个选方法。

BrowseComp-Plus 是我最希望 RL 论文多用的。Live-web API 会让「我们比 Search-R1 高 4 个点」几乎不可解释。固定语料才能说清增益来自 retriever、策略，还是更幸运的 SERP。

## 我真正在反复想的几件事

不想忘掉的几条。

只打 outcome 的 GRPO，在搜索轨迹上是欠定的。Search-R1++（2 月的工作，但这个观察一直成立）已经报过：这个设定里 GRPO 是最不稳定的优化器，F1 奖励会塌成「拒绝给答案」，除非加上 action-level penalty。MemSearcher 的 multi-context GRPO 是在把 credit 往 turn 上送。方向对。我还没看到一个让人信服的 token / span 级故事，去回答「这句话被检索到，所以答案才对」。

过早承诺是搜索特有的失败模式，但可以推广。HypoSearch 对分叉的分析，很像一个不会探索的策略。第一个 query 稍偏，后面整条轨迹就变成辩护机器。先分支再比较，今天还是 harness 技巧。它不必永远停在 harness 里。

Retriever 和 agent 不该分开训。ITER 的消融说：原问题加历史子查询是最稳的 query 表示，曾经有用的文档是最强的负例。这既是模型问题，也是接口问题。

评测现在已经是方法的一部分。如果 LiveBrowseComp 的排名对不上 BrowseComp，那么「BrowseComp SOTA」是关于记忆加搜索的声明，不是关于搜索。我更愿意成对报告：一个静态、可拆开的数字（BrowseComp-Plus），一个在线、有时间窗的数字（LiveBrowseComp 或 DR-Arena）。

我还不确定这个方向有没有决定：search agent 到底是 *偶尔检索的推理器*，还是 *偶尔思考的检索器*。过去四个月的论文在悄悄把票投给后者，却还在用为前者设计的指标做评价。这个错位，是我一直转回来的地方。
